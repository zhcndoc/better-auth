OAuth 客户端是使用你的提供者为用户登录，或调用你的 API 的应用。你可以自行创建客户端、允许已登录用户创建客户端，或允许客户端自行注册。

## Client types

客户端的两个属性彼此独立：

* **公有或机密客户端**（[RFC 6749 §2.1](https://datatracker.ietf.org/doc/html/rfc6749#section-2.1)）。公有客户端将 `token_endpoint_auth_method` 设为 `"none"`。机密客户端可使用 `client_secret_basic`、`client_secret_post` 或 [`private_key_jwt`](#private-key-jwt)。
* **`application_type`**（[OIDC Registration §2](https://openid.net/specs/openid-connect-registration-1_0.html#ClientMetadata)）。可设为 `web`（默认值）或 `native`。它只决定客户端可以注册哪些[重定向 URI](#redirect-uri-forms)。

原生客户端可以是机密客户端，Web 客户端也可以是公有客户端。移动端、桌面端或单页应用中随应用分发的密钥可能被提取，因此这类应用应注册为公有客户端（[RFC 8252 §8.5](https://datatracker.ietf.org/doc/html/rfc8252#section-8.5)）。只有在密钥保存在你管理的服务器上时，才应使用机密客户端。

## Manage clients

若要创建归已登录用户，或归 [`clientReference`](#organizations) 返回的组织所有的客户端，请发送 [RFC 7591 §2](https://datatracker.ietf.org/doc/html/rfc7591#section-2) 定义的客户端元数据。

<APIMethod path="/oauth2/create-client" method="POST" requireSession>
  ```ts
  type createOAuthClient = {
    /**
     * Redirect URIs for the authorization code flow.
     */
    redirect_uris?: string[] = ["https://client.example.com/callback"]
    /**
     * Display name shown on the consent screen.
     */
    client_name?: string = "My Client"
    /**
     * How the client authenticates at the token endpoint. Use `"none"` for a public client.
     */
    token_endpoint_auth_method?: "none" | "client_secret_basic" | "client_secret_post" | "private_key_jwt" = "client_secret_basic"
    /**
     * Controls redirect URI validation.
     */
    application_type?: "web" | "native" = "web"
    /**
     * Space-separated scopes the client may request.
     */
    scope?: string = "openid profile email"
  }
  ```
</APIMethod>

使用 `client_secret_basic` 或 `client_secret_post` 的客户端只会在此响应中获得 `client_secret`，因此请立即保存。公有客户端和 `private_key_jwt` 客户端只会获得 `client_id`。

大多数其他客户端端点都需要 `client_id`。每个端点都要求会话，下表列出了例外情况：

| 服务器方法                      | 路径                             | 方法    | 用途                                                       |
| ------------------------------ | -------------------------------- | ------- | ---------------------------------------------------------- |
| `getOAuthClient`               | `/oauth2/get-client`             | `GET`   | 读取该用户或组织拥有的客户端。                             |
| `getOAuthClientPublic`         | `/oauth2/public-client`          | `GET`   | 读取要在授权同意页展示的公开字段。                         |
| `getOAuthClientPublicPrelogin` | `/oauth2/public-client-prelogin` | `POST`  | 在登录页读取相同信息。无需会话，见下文。                   |
| `getOAuthClients`              | `/oauth2/get-clients`            | `GET`   | 列出该用户或组织拥有的客户端。                             |
| `updateOAuthClient`            | `/oauth2/update-client`          | `POST`  | 使用 `{ client_id, update }` 更新客户端。                  |
| `adminUpdateOAuthClient`       | `/admin/oauth2/update-client`    | `PATCH` | 仅限服务器调用，也可更新受限字段。                         |
| `rotateClientSecret`           | `/oauth2/client/rotate-secret`   | `POST`  | 签发新密钥，旧密钥会立即失效。                             |
| `deleteOAuthClient`            | `/oauth2/delete-client`          | `POST`  | 删除客户端。                                               |

创建后无法更改 `token_endpoint_auth_method`，更新操作也无法设置密钥。客户端密钥不会过期，因此要停用密钥时，请调用 `rotateClientSecret` 轮换它。

若要在登录页读取客户端的公开字段，请设置 `allowPublicClientPrelogin: true`，以启用 `getOAuthClientPublicPrelogin`。此方法需要有效且经过签名的 `oauth_query`，但该查询不会绑定到要读取字段的客户端。任何人都可以通过发起授权请求获得此查询。因此，启用该选项后，无需账户即可读取所有已启用客户端的公开字段，包括 `contacts`。

### Restricted fields

只有仅限服务器调用的 `adminCreateOAuthClient` 和 `adminUpdateOAuthClient` 方法可以设置以下字段：

* `skip_consent`：跳过授权同意页。用于[受信任客户端](#trusted-clients)。
* `enable_end_session`：允许客户端[结束用户会话](/docs/plugins/oauth-provider/openid-connect#rp-initiated-logout)。
* `require_pkce`：仅创建时可设置。设为 `false` 后，机密客户端可以跳过 [PKCE](/docs/plugins/oauth-provider/tokens#pkce)，这会移除针对授权码被截获和注入的防护。请保留默认值 `true`。
* `client_credentials_scopes`：请参阅[客户端凭据 scope](#client-credentials-scopes)。
* `resources`：仅创建时可设置。将客户端关联到[资源](/docs/plugins/oauth-provider/tokens#resources)。设置了 `resourcePrivileges` 时，它必须批准每个资源的 `link` 操作。
* `disabled`：仅更新时可设置。暂停客户端。
* `metadata`：附加到客户端的数据。公开端点不会返回这些数据，但客户端所有者以及[拥有客户端的组织](#an-organization-owns-the-client)成员可以读取。请勿在此存储密钥。

这两个方法均：

* 需要已登录用户的会话，并且需要传入会话请求头
* 会运行 [`clientPrivileges`](#client-crud-privileges)
* 不会检查用户是否为管理员

因此，只能从管理员可访问的服务器代码中调用这两个方法。浏览器使用会话 Cookie 调用该代码时，请先[检查请求的 `Origin`](/docs/reference/security#csrf-protection)。除[客户端 CRUD 权限](#client-crud-privileges)中所述的一种例外外，`adminUpdateOAuthClient` 还要求用户拥有该客户端。

管理员更新时，应将变更放在 `update` 下：

```ts title="admin-update-oauth.ts"
await auth.api.adminUpdateOAuthClient({
  headers: request.headers,
  body: {
    client_id: "client-id",
    update: {
      skip_consent: true, // [!code highlight]
      enable_end_session: true, // [!code highlight]
    },
  },
});
```

若要暂停客户端而不删除它，请设置 `disabled: true`；恢复时将其设为 `false`。已禁用的客户端无法获取新令牌，令牌核查也会将其现有令牌报告为非活跃。JWT 访问令牌会一直有效，直到过期。如果资源服务器在本地验证 JWT 且需要立即停用令牌，就必须自行检查客户端状态。

### Client credentials scopes

客户端必须先获得授权才能使用 `client_credentials` 授权许可，其 `scope` 不适用于此授权许可。若要启用此功能：

1. 定义 [`clientPrivileges`](#client-crud-privileges)，使其批准 `configure-client-credentials-scopes` 操作。
2. 使用 `adminCreateOAuthClient` 或 `adminUpdateOAuthClient` 设置非空的 `client_credentials_scopes`。客户端必须是机密客户端，并在 `grant_types` 中列出 `client_credentials`。每个 scope 都必须包含在 `scopes` 中，且不能是 `openid`、`profile`、`email` 或 `offline_access`。

令牌请求可以申请这些 scope 中的任意项。省略 `scope` 时会获得全部 scope。动态注册、CIMD 和 `createOAuthClient` 可以声明此授权许可，但无法设置此列表。

## Dynamic client registration

若要允许客户端自行注册，请设置 `allowDynamicClientRegistration`。随后，Better Auth 会在 `POST /oauth2/register` 接受注册请求（[RFC 7591 §3](https://datatracker.ietf.org/doc/html/rfc7591#section-3)）。默认情况下，调用者需要会话和 `create` 权限。

```ts title="auth.ts"
oauthProvider({
  allowDynamicClientRegistration: true, // [!code highlight]
})
```

若还要允许未登录的客户端注册，请在 `allowDynamicClientRegistration` 旁设置 `allowUnauthenticatedClientRegistration: true`。此后，互联网上的任何人都可以注册客户端：

* 注册者可以自行选择客户端名称、标志和重定向 URI。
* 客户端[没有所有者](#an-organization-owns-the-client)，因此无人能通过客户端端点管理它。
* 客户端不能使用 `client_credentials`。

优先考虑使用 CIMD 或初始访问令牌。如果启用开放注册，请保持[速率限制](/docs/concepts/rate-limit)开启。

若要从客户端应用发起注册，请调用 `authClient.oauth2.register({ client_name, redirect_uris })`。响应中会包含新的 `client_id`。使用 `client_secret_basic` 或 `client_secret_post` 的客户端也会获得 `client_secret`。只有此响应会包含该密钥，因此请立即保存。

<Callout type="info">
  对于未提前注册的公有客户端（例如 MCP 客户端），建议使用 [Client ID Metadata Documents](/docs/plugins/cimd)。客户端会在 HTTPS URL 上托管元数据，并将该 URL 用作自己的 `client_id`。
</Callout>

若要允许软件在没有用户会话时注册，请定义 `validateInitialAccessToken`。它会收到 `initialAccessToken`（来自 `Authorization: Bearer <token>` 的令牌）、请求 `headers` 和请求的 `clientMetadata`。返回 `false` 会以 401 `invalid_token` 拒绝请求；返回对象则表示接受。对象中的可选 `referenceId` 用于设置所有者。未提供该值时，客户端[没有所有者](#an-organization-owns-the-client)。未定义此回调时，发送到 `/oauth2/register` 的 Bearer 令牌会被拒绝。

请注意：

* 请以恒定时间比较令牌。
* 将 `clientMetadata` 视为不可信数据：它由注册者自行声明，尚未经过完整验证。
* 这些令牌应由你的应用签发和撤销（[RFC 7591 §3](https://datatracker.ietf.org/doc/html/rfc7591#section-3)）。
* 启用 [Bearer](/docs/plugins/bearer) 插件时，可解析为会话的 Bearer 值会被视为该会话，而不是初始访问令牌。

注册选项：

| 选项                                        | 默认值   | 作用                                                                                                                                                                                                                                                                          |
| ------------------------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `clientRegistrationDefaultScopes`          | `scopes` | 每个注册客户端都可以申请的 scope。                                                                                                                                                                                                                                            |
| `clientRegistrationAllowedScopes`          | 无       | 在默认值之外额外允许的 scope。                                                                                                                                                                                                                                                |
| `clientRegistrationClientSecretExpiration` | 永不过期 | 动态注册并获得密钥的客户端会收到 `client_secret_expires_at` 值。`"30d"` 这样的字符串表示自注册起计算的时长。数字（Unix 秒数）或 `Date` 表示固定时间。到期后 Better Auth 不会拒绝该密钥。 |
| `clientRegistrationRequirePKCE`            | `true`   | 设为 `false` 后，已注册的机密客户端可以跳过 PKCE，从而移除针对授权码被截获和注入的防护。公有客户端**始终需要** PKCE。                                                                                         |
| `clientRegistrationDefaultApplicationType` | `"web"`  | 注册请求未提供 `application_type` 时使用的值：`"web"`、`"native"` 或 `"infer"`（若任意重定向 URI 使用自定义 scheme 或 `http` loopback，则推断为 native）。                                                     |

动态注册和 CIMD 注册会将全部默认 scope 和允许的 scope 存储在每个客户端上。注册请求中的 `scope` 只会与该集合进行核对，不会被存储。默认集合为 `scopes`，也就是服务器定义的所有 scope。启用开放注册时，请将 `clientRegistrationDefaultScopes` 设为这些客户端所需的最小集合。

注册时只保留服务器支持的请求 `grant_types`，并在响应中返回实际注册的授权方式（[RFC 7591 §3.2.1](https://datatracker.ietf.org/doc/html/rfc7591#section-3.2.1)）。`createOAuthClient` 和 `adminCreateOAuthClient` 则会直接拒绝不支持的授权方式。如果注册请求中没有受支持的授权方式，会以 `invalid_client_metadata` 失败。注册者可以改为申请提供者 `grant_types_supported` 元数据中列出的授权方式，或者由你将该授权方式添加到 `grantTypes`。不支持 `sector_identifier_uri`。

### Resources for registered clients

默认情况下，注册请求无法申请[资源](/docs/plugins/oauth-provider/tokens#resources)。若要允许注册客户端申请资源，请使用以下选项：

* `clientRegistrationDefaultResources` 会将每个新客户端关联到这些资源，包括 CIMD 和管理员创建的客户端；此选项不检查 `resourcePrivileges`。
* `clientRegistrationAllowedResources` 列出注册请求可以额外申请的资源。

所有值也必须包含在 `resources` 中。申请的资源不在这两个列表中、资源不存在或已禁用时，都会以 `invalid_target` 失败。`error_description` 会指出资源名称和对应原因。响应会列出已关联的 `resources`。

```ts title="auth.ts"
oauthProvider({
  resources: ["https://api.example.com/default", "https://api.example.com/optional"],
  clientRegistrationDefaultResources: ["https://api.example.com/default"], // [!code highlight]
  clientRegistrationAllowedResources: ["https://api.example.com/optional"], // [!code highlight]
})
```

### Redirect URI forms

`application_type` 决定客户端可以注册哪些重定向 URI（[OIDC Registration §2](https://openid.net/specs/openid-connect-registration-1_0.html#ClientMetadata)，[RFC 8252 §7](https://datatracker.ietf.org/doc/html/rfc8252#section-7)）：

| 格式                                                                                                           | 示例                               | `web` | `native` |
| -------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ----- | -------- |
| 非 loopback 主机上的 HTTPS                                                                                   | `https://app.example.com/callback` | 是    | 是       |
| 任意端口的 HTTP loopback（[RFC 8252 §7.3](https://datatracker.ietf.org/doc/html/rfc8252#section-7.3)）       | `http://127.0.0.1:8787/callback`   | 否    | 是       |
| 反向域名私用 scheme（[RFC 8252 §7.1](https://datatracker.ietf.org/doc/html/rfc8252#section-7.1)）            | `com.example.app:/callback`        | 否    | 是       |
| 带主机和路径的自定义 scheme                                                                                 | `myapp://example.app/callback`     | 否    | 是       |

HTTP loopback URI 必须使用 `localhost`、`127.0.0.1` 或 `[::1]`，因此 `127.1` 等写法会被拒绝。loopback 地址上的 HTTPS 和其他主机上的 HTTP 也会被拒绝。Better Auth 还会拒绝片段、凭据、格式错误的 URI，以及 `javascript:` 和 `file:` 等保留 scheme。

<Callout type="warn">
  [RFC 8252 §8.4](https://datatracker.ietf.org/doc/html/rfc8252#section-8.4) 要求拒绝不含句点的私用 scheme，但为了兼容原生应用，Better Auth 会接受此类 scheme。其他应用可能声明相同的 scheme 并收到授权码，因此这些客户端应始终启用 PKCE。
</Callout>

## Custom redirect URI validation

申请的重定向 URI 必须与已注册的 URI 完全匹配。精确匹配可防止攻击者将授权码重定向到客户端未注册的 URI。唯一例外是原生客户端 loopback URI 的端口。例如，已注册的 `http://127.0.0.1:8787/callback` 也会匹配 `http://127.0.0.1:51234/callback`，但不会匹配 `http://localhost:51234/callback`。

若要更改可接受的 URI，请设置 `validateRedirectUri`。它会收到申请的 URI、客户端已注册的 URI，以及内置匹配的 `defaultResult`。返回 `true` 表示接受该 URI。此回调的结果会取代内置匹配逻辑，因此对于未处理的 URI，请返回 `defaultResult`：

```ts title="auth.ts"
oauthProvider({
  validateRedirectUri: (uri, registeredUris, defaultResult) => {
    if (defaultResult) return true;
    if (!registeredUris.includes("https://app.example.com/api/auth/callback")) return false;
    try {
      const url = new URL(uri);
      return url.protocol === "https:" && url.port === "" && url.search === "" &&
        url.hostname.endsWith(".preview.example.com") &&
        url.pathname === "/api/auth/callback";
    } catch {
      return false;
    }
  },
})
```

运行回调前，Better Auth 只会拒绝格式错误的 URI、凭据、片段、`javascript:` 等危险 scheme，以及非 loopback 主机上的 HTTP。回调接受的 URI 不受[重定向 URI 格式](#redirect-uri-forms)规则约束。此回调适用于所有客户端。返回 `false` 或抛出错误会拒绝该 URI，并将早期授权错误发送到服务器错误页，而不是客户端。

<Callout type="warn">
  接受额外 URI 会放宽 [RFC 9700 §2.1](https://datatracker.ietf.org/doc/html/rfc9700#section-2.1) 的精确匹配要求。只接受你控制且不可信用户无法部署内容的主机，并固定 scheme、主机后缀、端口、路径和查询参数。如果不可信客户端可以任意注册 URI，那么与 `registeredUris` 匹配并不能证明客户端身份。
</Callout>

启用[成对主体标识符](/docs/plugins/oauth-provider/openid-connect#pairwise-subject-identifiers)时，每个被接受的主机都会与客户端首个注册 URI 共用同一 sector，因此也会使用相同的 `sub`。

## Private key JWT

使用 `private_key_jwt` 时，客户端会通过自己的密钥签署 JWT 来完成身份验证，而不是使用共享密钥（[RFC 7523 §3](https://datatracker.ietf.org/doc/html/rfc7523#section-3)，[OIDC Core §9](https://openid.net/specs/openid-connect-core-1_0.html#ClientAuthentication)）。若要启用此方式，请将客户端公钥注册为 `jwks` 或 `jwks_uri`，不能同时使用两者：

```ts title="admin-create-oauth.ts"
await auth.api.adminCreateOAuthClient({
  headers: request.headers,
  body: {
    redirect_uris: ["https://app.example.com/callback"],
    token_endpoint_auth_method: "private_key_jwt",
    jwks: { keys: [{ kty: "EC", crv: "P-256", kid: "key-1", x: "...", y: "..." }] },
  },
});
```

对于主机不受你控制的客户端，建议直接内联 `jwks`。

* `jwks` 必须是 JWK Set 对象，其中 `keys` 数组包含至少一个签名公钥。EC 密钥使用 P-256、P-384 或 P-521；OKP 密钥使用 Ed25519。
* `jwks_uri` 必须是公网主机上的 HTTPS URL。除非其来源与 CIMD `client_id` 的来源相同，否则必须将其来源加入 [`trustedOrigins`](/docs/reference/options#trustedorigins)。`trustedOrigins` 适用于整个应用，因此该来源也会被信任用于重定向和请求。

客户端会发送 `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` 和经过签名的 `client_assertion`，而不是密钥。断言使用 `RS256`、`RS384`、`RS512`、`PS256`、`PS384`、`PS512`、`ES256`、`ES384`、`ES512` 或 `EdDSA` 签名，并且必须包含：

| 声明  | 要求                                                                          |
| ----- | ----------------------------------------------------------------------------- |
| `iss` | `client_id`                                                                   |
| `sub` | `client_id`                                                                   |
| `aud` | 接收该断言的端点 URL，或提供者的 issuer                                      |
| `exp` | 必填。有效期不得超过 `assertionMaxLifetime`（默认 300 秒）                   |
| `jti` | 必填。每个断言都必须使用唯一值                                               |
| `iat` | 可选。若提供，则不能早于 `assertionMaxLifetime`                              |

### Rotating client keys

若要允许内联 `jwks` 的客户端在没有用户会话时替换密钥，请设置 `allowClientKeyRotation: true`。客户端随后调用 `POST /oauth2/client/rotate-keys`。请求体包含 `client_assertion`、`client_assertion_type` 和完整的新 `jwks`。断言必须由当前密钥签名，其 `aud` 必须是密钥轮换端点的 URL。

新密钥集合中未包含的密钥会立即失效。若要无停机轮换密钥，请先发送包含新旧密钥的集合，然后只发送新密钥。竞争失败的请求会返回 409；如果其密钥已被移除，则会返回 401。

<Callout type="info">
  使用内存 adapter，或将 `advanced.database.generateId` 设为 `"serial"` 时，提供者会拒绝启动此选项，因为这两种配置都无法保证断言只能使用一次。
</Callout>

## Trusted clients

若要跳过对第一方应用的数据库查询（其重定向 URI 由你控制），请将其客户端 ID 列在 `cachedTrustedClients` 中。若还要跳过授权同意页，请为每个客户端设置 `skip_consent`。

<Callout type="warn">
  设置了 `skip_consent` 的客户端可以在未经用户同意的情况下，为任意已登录用户获取授权码，因此控制其重定向 URI 的人也就能控制这些授权码。客户端所有者仍可通过 `updateOAuthClient` 更改 `redirect_uris`。设置了 `clientReference` 时，所有者是组织，其任意成员都可以进行此更改。只为 `cachedTrustedClients` 中的客户端设置 `skip_consent`（客户端端点无法更改此列表），或者在 [`clientPrivileges`](#client-crud-privileges) 中拒绝这些客户端的 `update` 操作。不要为公有原生客户端设置此选项。设备上的任何应用都可以发起流程并接收重定向；若攻击者发起流程，PKCE 也无法提供保护。
</Callout>

* 每台服务器都会将列表中的客户端保存在内存中，直到服务器重启。
* 客户端端点（包括管理员方法）无法更改这些客户端。
* 若要禁用客户端或更改其重定向 URI，请编辑数据库记录并重启所有实例。

```ts title="auth.ts"
oauthProvider({
  cachedTrustedClients: new Set(["internal-dashboard", "mobile-app"]), // [!code highlight]
})
```

## Client CRUD privileges

若要限制已登录用户可以执行的客户端操作，请定义 `clientPrivileges`。未定义时，除 `configure-client-credentials-scopes` 外，所有已登录用户都可以执行所有操作。定义后，返回 `true` 表示允许操作，返回 `false` 或 `undefined` 表示拒绝。操作被拒绝时会返回 401。

<Callout type="warn">
  默认情况下，任何已登录用户都可以通过 `createOAuthClient`，或在动态注册时提供会话来创建 OAuth 客户端。如果应用允许公开注册，那么任何人都可以创建客户端，并自行指定名称、标志和重定向 URI，再将其展示在授权同意页上。未设置 `scope` 创建的客户端可能会申请服务器定义的所有 scope。请定义 `clientPrivileges`，确保只有受信任用户可以执行 `create`。
</Callout>

此回调会收到 `action`（`create`、`read`、`update`、`delete`、`list`、`rotate` 或 `configure-client-credentials-scopes`）、`user`、`session`、`headers`，以及已有客户端的 `clientId`。`clientId` 来自请求，不能证明客户端存在或其所有者身份。

所有权会在此回调之后检查，因此返回 `true` 并不会授予访问其他所有者客户端的权限。有一个例外：当 `adminUpdateOAuthClient` 只更改 `client_credentials_scopes`，且回调同时批准 `update` 和 `configure-client-credentials-scopes` 时，可以更改其他所有者的客户端。

```ts title="auth.ts"
oauthProvider({
  clientPrivileges: async ({ headers, session }) => {
    if (!session?.activeOrganizationId) return false;
    const member = await auth.api.getActiveMember({ headers });
    return member?.role === "owner";
  },
})
```

## Organizations

若要让组织（而不是用户）拥有新客户端，请设置 `clientReference`。它会收到已登录用户的 `user` 和 `session`。返回所有者的 ID；返回 `undefined` 则将用户设为所有者。客户端所有者在创建时确定，之后不会更改。以下示例返回当前[组织](/docs/plugins/organization)：

```ts title="auth.ts"
oauthProvider({
  clientReference: ({ session }) =>
    (session?.activeOrganizationId as string | undefined) ?? undefined,
})
```

当前组织可能在用户离开组织后仍被保留。`clientPrivileges` 会先运行并收到请求头，因此请像上面的示例一样在其中检查成员身份。

组织与客户端之间有两种关联方式：

* **组织使用客户端。** 多个组织可以共用一个无所有者客户端，例如第三方应用或 CIMD 客户端。每份授权同意都会记录其所属组织。
* **组织拥有客户端。** 组织成员可以通过上述端点管理客户端，包括其重定向 URI。只有在组织能够控制客户端时，才应将客户端交由组织所有。

### An organization uses the client

若要按组织记录授权同意，请像[登录后页面](/docs/plugins/oauth-provider/sign-in-flow#post-login-screen)示例一样，从 `postLogin.consentReferenceId` 返回组织。之后，`customAccessTokenClaims` 会通过 `referenceId` 收到组织，但 ID 令牌和 UserInfo 回调不会收到：

```ts title="auth.ts"
oauthProvider({
  // postLogin: see Post-login screen
  customAccessTokenClaims: ({ referenceId }) => ({ "https://example.com/org": referenceId }),
})
```

删除授权同意只会移除该组织的授权同意，不会撤销已签发的令牌。若要按客户端添加组织声明，请参阅[客户端专属访问令牌声明](/docs/plugins/oauth-provider/tokens#client-specific-access-token-claims)。

### An organization owns the client

成员创建客户端，或在注册时提供会话，都会使客户端归 `clientReference` 返回的组织所有。对于自行注册的软件，可让组织管理员在应用中签发初始访问令牌，并从 `validateInitialAccessToken` 返回该组织：

```ts title="auth.ts"
oauthProvider({
  allowDynamicClientRegistration: true,
  validateInitialAccessToken: async ({ initialAccessToken }) => {
    const token = await findRegistrationToken(initialAccessToken); // your lookup
    return token ? { referenceId: token.organizationId } : false;
  },
})
```

以下情况会使客户端没有所有者：

* 客户端通过开放注册或 [CIMD](/docs/plugins/cimd) 文档创建。
* 客户端使用初始访问令牌注册，但验证结果未返回 `referenceId`。
* 客户端有 `referenceId`，但未配置 `clientReference`。

客户端端点会将此类客户端视为无所有者：

* 列表查询不会返回此客户端。
* 读取、更新、禁用、删除客户端或轮换其密钥都会返回 401。
* 只有[客户端 CRUD 权限](#client-crud-privileges)中用于更新 `client_credentials_scopes` 的管理员操作可以更改此客户端。

请改为直接在数据库中管理。

若各组织将软件作为自己的客户端运行，应改用初始访问令牌进行注册。
